# The CUI workflow

This repo is set up so that an AI-written codebase stays one you can actually hold in your
head. Four rules, enforced rather than remembered:

1. **Product Function milestones are agreed before any code is written.**
2. **The repo structure is locked before any code is written.**
3. **Every commit is recorded with its coverage, its demo, and what it did for a milestone.**
4. **Every commit can explain itself**, in a walkthrough you can interrogate line by line.

## Running it

```bash
npm run cui            # dashboard at http://localhost:4317
npm run cui:status     # the same thing, in the terminal
npm run cui:doctor     # check the project is wired up correctly
```

Without a root `package.json`: `node cui/bin/cui.mjs serve`.

## The gates

A `PreToolUse` hook blocks writes to implementation files until:

- `.cui/product-functions.yaml` has milestones, **and**
- `.cui/blueprint.yaml` has `locked: true`

Docs, `.cui/`, `demos/` and `cui/` stay writable throughout. To lift the gates entirely,
set `enforce: false` in `.cui/config.yaml` — but then you are back to hoping, which is what
this whole setup exists to replace.

## The files

| File | What it is | Who writes it |
| --- | --- | --- |
| `.cui/product-functions.yaml` | Milestones and acceptance criteria | `/cui:pf` |
| `.cui/blueprint.yaml` | Directory layout, boundary rules, entry points | `/cui:blueprint` |
| `.cui/commands.yaml` | Every runnable command, searchable in the CUI | `/cui:blueprint` |
| `.cui/config.yaml` | Ports, coverage paths, thresholds | you |
| `.cui/cui.db` | Projection of the above plus git history | generated, gitignored |
| `ARCHITECTURE.md` | Human-readable blueprint | generated by `/cui:blueprint` |
| `demos/` | Per-commit evidence | `/cui:ship` |

The YAML files are the source of truth. The database is rebuildable at any time:

```bash
node cui/bin/cui.mjs sync && node cui/bin/cui.mjs backfill
```

## Committing

Use `/cui:ship`, not `git commit`. It runs the tests with coverage, decides whether the commit
needs a visual demo and produces one, scores the change against the milestones, and writes
trailers the CUI parses:

```
PF: PF-2 progress (PF-2.1, PF-2.3 met)
Coverage: project 78.4% (+1.2), diff 91.3%
Demo: demos/004-revenue-chart - 12 months rendered from seeded data
Blueprint: unchanged
```

**Diff coverage** — the share of the lines *this commit added* that tests actually execute —
is the number worth watching. Project coverage can rise while a commit adds nothing but
untested code.

A `post-commit` git hook records commits made outside Claude Code too, so the history in the
CUI is never partial. Commits without trailers show up flagged as unscored rather than
silently missing.

## Demos

Commits that change observable behaviour carry evidence in `demos/<NNN>-<slug>/`:

```
demos/004-revenue-chart/
  demo.md      the narrative: claim, evidence, and what it does NOT prove
  run.sh       regenerates every artifact below; exits non-zero if a check fails
  01-*.txt     verbatim terminal output
  02-*.md      sample rows
  03-*.png     screenshots or charts
```

Commits that don't need one record *why* — `Demo: skipped - pure refactor, output
byte-identical on the fixture corpus`. "Trivial" is rejected.

## Walkthroughs and questions

On any commit page: **Generate walkthrough**. This runs Claude Code headless against the
repo — it reads the commit, the surrounding files and the blueprint, and writes it up like an
engineering blog post. A copy lands in `.cui/walkthroughs/<sha>.md` so it is greppable.

Then ask about it. Click **ask about this** on any snippet, or open a file in the Changes tab
and click a line number, and ask. Answers are grounded in the code as it stood at that commit.

Requires the `claude` CLI on PATH. Set `claude_bin` in `.cui/config.yaml` if it lives
somewhere unusual.

## Coverage setup

The CUI auto-detects the usual artifacts:

| Tool | File |
| --- | --- |
| Jest, Vitest, c8, nyc | `coverage/lcov.info`, `coverage/coverage-final.json` |
| pytest-cov, coverage.py | `coverage.xml`, `coverage.json` |
| Go | `coverage.out` |
| JaCoCo, Cobertura | `coverage.xml` |

Set `coverage_command` in `.cui/config.yaml` so `node cui/bin/cui.mjs coverage run` knows how to produce it.
